# Tool-Craft 产品需求文档

## 一、产品概述

### 1.1 产品名称

**Tool-Craft**

### 1.2 产品定位

Tool-Craft 是一个持续提供实用工具的在线工具平台。

平台通过两条相互独立的产品线，为不同用户提供工具能力：

* **Web Tools**：面向普通用户，直接在浏览器中使用。
* **API Tools**：面向开发者、程序和 AI Agent，通过 API 调用。

两条产品线属于同一个工具生态，但不要求共享技术架构、运行时或具体实现。

产品的核心目标是：

> **以尽可能低的成本，持续增加有实际价值的工具。**

平台不以建立复杂的通用能力基础设施为目标，而是优先把每一个工具本身做好。

---

# 二、产品目标

## 2.1 核心目标

### Web Tools

让用户能够：

> **发现工具 → 打开工具 → 完成任务 → 获得结果**

整个过程应该尽可能简单、快速。

### API Tools

让开发者能够：

> **发现能力 → 阅读文档 → 调用 API → 获取结果**

API 应具备清晰、稳定、可自动化调用的特性。

---

## 2.2 长期目标

持续扩充工具数量和覆盖范围，使平台逐渐形成一个实用的工具集合。

工具数量可以从：

```text
10
 ↓
100
 ↓
1000+
```

逐步增长。

平台的扩展方式不是提前设计一个复杂的统一系统，而是：

> **先解决真实需求，再根据规模产生的问题逐步优化。**

---

# 三、目标用户

## 3.1 Web Tools 用户

主要面向需要快速完成某项任务的普通互联网用户。

典型场景：

* 临时格式化 JSON
* 压缩图片
* 转换图片格式
* 处理文本
* 生成或转换数据
* 调整颜色
* 使用各种开发辅助工具

用户通常不希望：

* 注册账号
* 学习复杂操作
* 配置大量参数
* 上传数据到不必要的服务器

---

## 3.2 API Tools 用户

主要面向：

* 开发者
* 后端程序
* 自动化程序
* AI Agent
* 其他第三方服务

他们更关注：

* API 是否稳定
* 输入输出是否明确
* 是否容易集成
* 是否有清晰文档
* 是否能够自动化调用
* 鉴权、限流和版本机制是否明确

---

# 四、产品整体结构

```text
                         Tool-Craft
                              │
                 ┌────────────┴────────────┐
                 │                         │
                 ▼                         ▼
             Web Tools                 API Tools
                 │                         │
          Browser / Local              Server / API
                 │                         │
             面向用户                  面向程序
```

两条产品线并行发展。

它们可以拥有相同或相似的工具，但不存在一一对应关系。

例如：

```text
Web Tools
├── Image Compressor
├── Image Converter
├── JSON Formatter
├── Color Picker
└── CSS Playground

API Tools
├── Image Processing API
├── OCR API
├── PDF API
└── AI Processing API
```

Web 中存在的工具不要求一定存在 API。

API 中存在的能力也不要求一定提供 Web 工具。

---

# 五、Web Tools

## 5.1 产品定位

Web Tools 是 Tool-Craft 的主要用户产品。

核心特点：

* 浏览器直接使用
* 操作简单
* 即时反馈
* 优先本地处理
* 尽量无需登录
* 尽量避免不必要的数据上传

---

## 5.2 Local-first

对于适合浏览器本地处理的任务，优先采用本地处理。

典型流程：

```text
用户
 ↓
Browser
 ↓
Local Processing
 ↓
结果
```

尤其对于：

* 图片
* 文件
* 文本
* 用户输入数据

应尽量避免没有必要的数据上传。

Local-first 不只是技术选择，也是产品体验的一部分：

> 用户可以更直接地理解自己的数据正在自己的设备上被处理。

---

## 5.3 无强制登录

普通 Web Tools 默认应该支持：

```text
打开
 ↓
使用
 ↓
获得结果
```

不因为统计、个性化等非核心需求强制用户注册。

如果某个工具未来确实需要账号体系，则根据实际需求单独设计。

---

## 5.4 工具独立性

每个工具应该是一个相对独立的产品单元。

新增工具的理想流程：

```text
发现需求
 ↓
设计工具
 ↓
实现工具
 ↓
加入分类
 ↓
发布
```

工具内部可以根据自身需求采用不同实现方式。

例如：

* JavaScript
* WebAssembly
* Web Worker
* WebGPU
* 第三方库

不要求所有工具使用完全相同的技术方案。

---

# 六、Web Tools 信息架构

## 6.1 工具分类

初期可以根据工具类型建立基础分类，例如：

```text
Web Tools
├── Image
├── Text
├── Developer
├── Design
├── File
├── Data
└── Other
```

分类不要求一次性设计完整。

随着工具数量增长，根据实际内容逐步调整。

---

## 6.2 首页

首页主要承担两个任务：

1. 让用户快速理解平台
2. 让用户快速找到工具

可以包含：

* 平台简介
* 工具分类
* 推荐 / 常用工具
* 工具搜索
* 工具列表

不应该为了展示平台能力而增加复杂交互。

---

## 6.3 工具列表

工具列表用于浏览和发现工具。

每个工具至少需要：

* 工具名称
* 简短描述
* 所属分类
* 工具入口

可以根据实际需求增加：

* 图标
* 标签
* 最近使用
* 推荐标记

---

## 6.4 工具页面

工具页面是 Web Tools 的核心页面。

基本原则：

> **用户进入页面后，应尽快知道“这个工具是做什么的，以及下一步应该做什么”。**

页面应围绕核心任务设计。

例如 JSON Formatter：

```text
JSON Formatter
────────────────────

输入 JSON
┌────────────────────┐
│                    │
│                    │
└────────────────────┘

[ Format ]

输出
┌────────────────────┐
│                    │
│                    │
└────────────────────┘
```

避免加入与核心任务无关的复杂流程。

---

# 七、API Tools

## 7.1 产品定位

API Tools 是面向程序调用的独立产品线。

其核心目标不是：

> 把 Web Tools 简单包装成 API。

而是：

> **为程序提供稳定、清晰、可自动化调用的工具能力。**

因此 API 可以拥有完全独立的产品设计。

---

## 7.2 API 核心能力

API Tools 根据实际需求逐步提供：

* API Key / 鉴权
* 请求认证
* 输入 Schema
* 输出 Schema
* 错误处理
* 限流
* 版本管理
* SDK
* API 文档

这些机制属于 API 产品本身，不应该反向影响 Web Tools。

---

## 7.3 API 工具设计

API 工具应明确：

```text
Endpoint
Input
Output
Error
Authentication
Rate Limit
Version
```

例如：

```text
POST /v1/image/compress
```

输入：

```text
Image
Quality
Format
```

输出：

```text
Processed Image
Metadata
```

具体接口形式根据实际工具需求确定。

---

# 八、Web 与 API 的关系

Web 与 API 的关系是：

> **同属一个工具生态，但保持产品和工程上的独立。**

不采用以下模式：

```text
Capability
    ↓
Universal Runtime
    ↓
Web / API / MCP
```

也不要求：

```text
一个工具
   ↓
必须同时拥有
   ├── Web
   ├── API
   └── MCP
```

而是：

```text
Tool-Craft
   │
   ├── Web Tools
   │
   └── API Tools
```

当两个产品线出现实际重复需求时，再考虑共享代码或基础设施。

---

# 九、共享原则

允许共享：

* 品牌
* 产品名称
* 分类
* 文档
* 设计资产
* 工具描述
* UI 组件
* 通用代码
* 基础设施

但共享不是强制要求。

共享必须满足：

> **共享带来的收益大于共享本身带来的复杂度。**

如果为了共享需要建立大量抽象，则优先保持独立。

---

# 十、工具开发原则

## 10.1 优先解决真实需求

新增工具时优先考虑：

* 用户是否真的需要
* 是否能明显降低某项任务的成本
* 是否能够简单完成
* 是否值得长期维护

而不是优先考虑：

* 如何进入统一能力体系
* 如何适配未来所有 Runtime
* 如何同时支持 Web、API、MCP、Agent

---

## 10.2 简单优先

如果一个工具只需要普通 JavaScript 就能完成，就不应该为了架构统一增加复杂层次。

例如：

```text
JSON Formatter
    ↓
普通 Web 页面
    ↓
JavaScript
```

就可以直接实现。

---

## 10.3 工具内部允许自由设计

不同工具可以拥有不同：

* UI
* 交互
* 数据处理方式
* 技术实现
* 性能优化方案

平台只需要保持基本的产品一致性。

---

推荐结构：

```text
tool-craft/
├── apps/
│   ├── web/
│   │   └── src/
│   │       ├── pages/
│   │       ├── components/
│   │       ├── tools/
│   │       ├── categories/
│   │       └── lib/
│   │
│   └── api/
│       └── src/
│           ├── routes/
│           ├── middleware/
│           ├── schemas/
│           ├── services/
│           └── lib/
│
├── packages/
│   ├── ui/
│   └── config/
│
├── docs/
├── package.json
└── pnpm-workspace.yaml
```

---

# 十二、未来扩展

未来根据真实需求，可以增加：

* API
* MCP
* Agent 集成
* SDK
* 工作流
* 工具组合
* 批量处理
* 自动化

这些能力都不应该成为 Web Tools 初期的架构前提。

未来如果出现新的消费方式，可以自然扩展：

```text
Tool-Craft
   │
   ├── Web
   ├── API
   └── New Consumer
```

而不是要求所有工具进入统一 Runtime。

---

# 十三、非目标

以下内容不是项目初期目标：

### 13.1 通用能力平台

不提前建设：

```text
Capability
Runtime
Adapter
Universal Schema
Universal Executor
```

### 13.2 强制跨端复用

不要求：

```text
Web Tool
    ↕
API Tool
```

必须共享底层实现。

### 13.3 复杂账号体系

Web Tools 初期不以账号体系为核心。

### 13.4 工作流平台

初期不建设复杂的工具编排、节点连接和工作流系统。

### 13.5 Agent 平台

Agent 可以是未来的消费方式，但不是 Web Tools 初期的架构基础。

---

# 十四、产品演进策略

平台采用渐进式演进：

```text
阶段 1
简单工具
    ↓
阶段 2
工具数量增加
    ↓
发现重复问题
    ↓
提取公共能力
    ↓
阶段 3
形成稳定基础设施
    ↓
阶段 4
根据真实需求扩展 API / MCP / Agent 等能力
```

核心原则：

> **问题出现之后再抽象，而不是为了未来可能出现的问题提前抽象。**

---

# 十五、成功标准

平台初期不以复杂的技术指标作为主要目标，而关注：

### Web Tools

* 工具数量持续增长
* 新工具开发成本低
* 用户能够快速完成任务
* 工具体验简单直接
* 本地处理能力不断增加
* 用户不需要为了使用工具承担额外成本

### API Tools

* API 能力持续增加
* 接口稳定
* 输入输出清晰
* 文档清晰
* 易于程序和 Agent 调用

### 平台整体

最终形成：

```text
更多有价值的工具
        ↓
更多用户使用
        ↓
发现新的需求
        ↓
增加新的工具
        ↓
形成持续增长的工具生态
```

---

# 十六、最终产品原则

Tool-Craft 遵循以下原则：

1. **工具价值优先**
2. **简单优先**
3. **Web 与 API 独立发展**
4. **Web Tools 优先 Local-first**
5. **尽量无需登录**
6. **工具保持独立**
7. **共享由实际需求驱动**
8. **允许不同工具使用不同技术**
9. **不为了未来场景过度设计**
10. **先把工具做好，再根据真实需求抽象**

最终可以概括为一句话：

> **先把工具做好，再根据真实需求抽象；而不是先建立抽象，再让工具适应抽象。**
